Decyzje

Techniczne. Wybrane przeze mnie, działam wg nich domyślnie. Veto jedną linią w Decyzje do podjęcia.md.

A1Stack: Vanilla+, bez frameworka i bundlera

Każdą zmianę robi agent w jednym przebiegu: czytaj, edytuj, test headless. Opcja B (Vite + Preact) to 5–8 rund i build przy każdej zmianie. Veto ma sens tylko przy >8 ekranach w pół roku.

A2Jedno repo = vault + kod

Obsidian pokazuje tylko notatki, pliki .html/.js są niewidoczne. Dwa repo dopiero przy drugim produkcie albo drugim współpracowniku.

A3Jakość = harness Playwright, nic więcej

Zielone = exit 0, puste *.errors, brak *.EXCEPTION. Bez CI, linterów, Spec Kitu, dopóki nie boli.

A4Runtime v1 = artefakt claude.ai

Tylko tam działa „Oceń z Claude” bez własnego backendu i klucza API. GitHub Pages dopiero, gdy ocena w stronie przestanie być potrzebna.

A5Podział pliku: najpierw data.js

Treść (instrukcje, zachęty, tematy, tygodnie) do osobnego pliku bez logiki. Tygodnie 4–12 to zmiany w treści, więc agent dotyka jednego pliku. Potem map.js z wstrzykiwanym kontekstem, styles.css, app.js. Recenzent oszacował 2 rundy.

A6Poprawki z recenzji R1–R6 przed treścią tygodnia 4

Najważniejsze: R1, zaliczenie dnia liczy się z aktualnej listy ćwiczeń, więc dodanie ćwiczeń do tygodnia 4 cofnie zaliczone dni i streak. Do tego: ucinany dziennik przy powrocie na mapę, błąd od dnia 85, sonda Claude odpalana bez kliknięcia, stary wynik oceny doklejany do nowego transkryptu.

Biznesowe i produktowe. Twoje. Każda ma rekomendację, kroki są w Decyzje do podjęcia.md.

Jak w tym pracować, krok po kroku

  1. Otwórz katalog plynnosc w Obsidianie jako vault. Zakładka Start jest w zakładkach. Czytaj: Start → Decyzje do podjęcia → Backlog.
  2. W Decyzje do podjęcia.md odhacz [x] i dopisz jedną linię „Decyzja: …” przy każdej pozycji, którą rozstrzygasz. Reszta idzie wg rekomendacji.
  3. Zrób B1 (GitHub) jako pierwsze: utwórz prywatne repo, a w sesji Claude Code powiedz „podłącz repo jestemalek1/plynnosc z prawem push i wypchnij main”.
  4. Każda sesja agenta zaczyna od CLAUDE.md, bierze jedną pozycję z backlogu albo jedną decyzję do wdrożenia, kończy zielonym harnessem i wpisem w Decision log.
  5. Większe zmiany (stan, timer, mapa, ocena, logika dnia): budowniczy → niezależny tester + recenzent → poprawki → publikacja. Małe (tekst, jedna funkcja): sam budowniczy + harness.
  6. Publikacja: narzędzie Artifact, read aktualnej wersji, potem publish na ten sam URL, bez podawania capabilities. Po publikacji jedno sprawdzenie na telefonie.
  7. Niedziela, 10 minut: Review.md. Czy decyzje są zapisane, czy harness zielony, czy artefakt = repo, czy w vaultcie nie ma transkryptów.
